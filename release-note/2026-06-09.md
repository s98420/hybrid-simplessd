# Hybrid SimpleSSD Release Note - 2026-06-09

## Overview

This update adds a Unix-domain RPC bridge between `jdp-raid-sim` and
`hybrid-simplessd`.

The bridge allows JDP RAID to send each generated per-drive command through
the existing Hybrid SimpleSSD path:

```text
jdp-raid-sim DriveRequest
  -> NvmeRpcClient
  -> Unix-domain socket
  -> IGL::RPCServer
  -> BIL::BIO
  -> SIL::NVMe::Driver
  -> SimpleSSD NVMe controller
  -> completion status and simulation ticks
```

The original in-memory JDP backend remains the default. RPC forwarding is only
enabled when `--nvme-rpc-socket-template` is specified.

## RPC Replay Hang Fix

Fixed a hang that occurred immediately after:

```text
[replay] submitting RAID drive commands ...
```

The RPC server previously received commands on the SimpleSSD event-engine
thread and called `engine.doNextEvent()` recursively while waiting for a BIO
completion. The first drive request could enter a runaway nested event loop,
causing one SimpleSSD drive to consume 100% CPU and continuously grow its
memory usage.

The RPC path now:

1. Receives socket commands on a dedicated RPC worker thread.
2. Schedules BIO submission onto the SimpleSSD event-engine thread.
3. Uses a blocking event loop while RPC mode waits for external commands.
4. Wakes the RPC worker only after the BIO completion callback runs.

This keeps all SimpleSSD/NVMe simulation events on the main event-engine
thread and preserves the synchronous line-based RPC protocol.

## Hybrid SimpleSSD RPC Server

Added:

```text
igl/rpc/rpc_server.hh
igl/rpc/rpc_server.cc
config/rpc.cfg
```

New global configuration:

```ini
# 0: request generator
# 1: trace replayer
# 2: Unix-domain RPC server
Mode = 2

RPCSocketPath = /tmp/hybrid-simplessd.sock
```

RPC-submitted requests use the existing NVMe command construction and
completion path. They are also labeled as `rpc` in
`request_latency.csv`.

## RPC Command Protocol

The protocol is synchronous and line based. Each command and response ends
with a newline.

Supported commands:

```text
INFO
READ <id> <tier> <lba> <nlb>
WRITE <id> <tier> <lba> <nlb>
MIGRATE <id> <src_tier> <src_lba> <dst_tier> <dst_lba> <nlb>
STOP
```

Tier values:

- `0`: SLC
- `1`: TLC

Successful I/O completion:

```text
OK <id> <status> <submit_tick> <complete_tick> <latency_tick>
```

`INFO` response:

```text
OK INFO <capacity_bytes> <block_size_bytes> <slc_bytes> <tlc_bytes> <current_tick>
```

## JDP RAID RPC Client

Added:

```text
jdp-raid-sim/src/device/nvme_rpc.py
jdp-raid-sim/tests/test_nvme_rpc.py
```

New CLI options:

```text
--nvme-rpc-socket-template
--nvme-rpc-timeout
```

The socket template must contain `{drive_id}` when multiple RAID drives are
used:

```text
/tmp/hybrid-simplessd-{drive_id}.sock
```

JDP maps its generated data type to the Hybrid SimpleSSD tier:

- `H`, `P`, and `Q` are sent to tier `0` (SLC).
- Other data types are sent to tier `1` (TLC).

/root/RAID_sim/hybrid-simplessd/build/simplessd-standalone

## Start One Hybrid SimpleSSD Server

The included `config/rpc.cfg` listens on:

```text
/tmp/hybrid-simplessd.sock
```

Start it with:

```bash
cd /root/RAID_sim/hybrid-simplessd
mkdir -p output/rpc

./build/simplessd-standalone \
  ./config/rpc.cfg \
  ./config/dtssd.cfg \
  ./output/rpc
```

The process waits for RPC commands until it receives `STOP`.

## Start One Server Per RAID Drive

Each Hybrid SimpleSSD process models one drive and therefore needs a unique
socket path and output directory.

For a four-drive RAID, prepare four simulation config files based on
`config/rpc.cfg`:

```text
config/rpc-drive-0.cfg -> RPCSocketPath = /tmp/hybrid-simplessd-0.sock
config/rpc-drive-1.cfg -> RPCSocketPath = /tmp/hybrid-simplessd-1.sock
config/rpc-drive-2.cfg -> RPCSocketPath = /tmp/hybrid-simplessd-2.sock
config/rpc-drive-3.cfg -> RPCSocketPath = /tmp/hybrid-simplessd-3.sock
```

Then start the four servers in separate terminals:

```bash
cd /root/RAID_sim/hybrid-simplessd

./build/simplessd-standalone config/rpc-drive-0.cfg config/dtssd.cfg output/drive-0
./build/simplessd-standalone config/rpc-drive-1.cfg config/dtssd.cfg output/drive-1
./build/simplessd-standalone config/rpc-drive-2.cfg config/dtssd.cfg output/drive-2
./build/simplessd-standalone config/rpc-drive-3.cfg config/dtssd.cfg output/drive-3
```

Create each output directory before starting its server.

## Run JDP RAID With Hybrid SimpleSSD

After all drive sockets exist, start JDP RAID:

```bash
cd /root/RAID_sim/jdp-raid-sim

python3 dt_raid_sim.py \
  --tracefile <TRACE_PATH> \
  --tracetype <MSR|FIO|ALIBABA> \
  --raid-type RAID5 \
  --raid-disks 4 \
  --chunk-size 4096 \
  --block-size 4096 \
  --data-placement ls \
  --tier-strategy STATIC \
  --nvme-rpc-socket-template '/tmp/hybrid-simplessd-{drive_id}.sock' \
  --nvme-rpc-timeout 30 \
  --output-dir ./logs/rpc-run
```

Without `--nvme-rpc-socket-template`, JDP RAID continues using the original
in-memory accounting backend.

## Let JDP RAID Manage SimpleSSD Processes

JDP RAID can now launch and manage the complete Hybrid SimpleSSD drive array.
This is the recommended startup method:

```bash
cd /root/RAID_sim/jdp-raid-sim

python3 dt_raid_sim.py \
  --tracefile <TRACE_PATH> \
  --tracetype <MSR|FIO|ALIBABA> \
  --raid-type RAID5 \
  --raid-disks 4 \
  --chunk-size 4096 \
  --block-size 4096 \
  --data-placement ls \
  --tier-strategy STATIC \
  --simplessd-root /root/RAID_sim/hybrid-simplessd \
  --output-dir ./logs/managed-rpc-run
```

From `--simplessd-root`, JDP automatically uses the newest available
`simplessd-standalone` from:

```text
build/simplessd-standalone
build-rpc/simplessd-standalone
simplessd-standalone
```

It also derives:

```text
config/rpc.cfg
config/dtssd.cfg
```

For each RAID drive, JDP automatically:

1. Generates a drive-specific RPC configuration.
2. Allocates a unique Unix socket under `/tmp/jdp-raid-sim-<pid>/`.
3. Creates `output-dir/simplessd/drive-<id>/`.
4. Starts and monitors one Hybrid SimpleSSD process.
5. Connects the RAID backend after all drive sockets are ready.
6. Sends `STOP` and reaps every process when simulation finishes or fails.

Startup progress is printed to the terminal:

```text
[SimpleSSD] launching 16 drives with ...
[SimpleSSD] ready 16/16 drives
[SimpleSSD] connecting RAID backend 16/16
[metadata] cache hit: ...
[replay] submitting RAID drive commands ...
```

Before replaying a full trace, a short managed-process smoke test can be run
with `--input-cmds`:

```bash
cd /root/RAID_sim/jdp-raid-sim

python3 dt_raid_sim.py \
  --tracefile /mnt/hgfs/Tools/MSR-Cambridge/web_3.csv \
  --tracetype MSR \
  --raid-type RAID5 \
  --raid-disks 16 \
  --chunk-size 524288 \
  --block-size 4096 \
  --data-placement ls \
  --tier-strategy STATIC \
  --simplessd-root /root/RAID_sim/hybrid-simplessd \
  --input-cmds 100 \
  --output-dir ./logs/managed-rpc-smoke
```

Remove `--input-cmds 100` to replay the complete trace.

Per-drive logs and generated configurations are stored under:

```text
<output-dir>/simplessd/drive-<id>/
```

Custom layouts can specify paths individually:

```text
--simplessd-executable
--simplessd-rpc-config
--simplessd-ssd-config
--simplessd-startup-timeout
```

## Stop A Server Manually

Use the Python RPC client to send `STOP`:

```bash
cd /root/RAID_sim/jdp-raid-sim

PYTHONPATH=src python3 -c \
  "from device.nvme_rpc import NvmeRpcClient; c=NvmeRpcClient('/tmp/hybrid-simplessd.sock'); c.close(stop_server=True)"
```

For a RAID array, send `STOP` to each drive socket.

## Current Behavior And Limitations

- RPC commands are processed synchronously, one command at a time per drive.
- One Hybrid SimpleSSD server process represents one RAID drive.
- JDP keeps its existing counters while also forwarding commands through RPC.
- JDP currently forwards read/write drive requests. Existing migration write
  plans are forwarded as their generated read/write traffic; direct
  `MIGRATE` protocol support is available for future integration.
- The RPC transport uses Unix-domain sockets and currently targets Linux.
