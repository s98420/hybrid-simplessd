# Hybrid SimpleSSD Release Note - 2026-06-08

## Overview

This update improves dual-tier SLC/TLC simulation, adds per-tier performance
reporting, and fixes build compatibility with newer GCC and glibc versions.

The most important change is that SLC and TLC NAND timing parameters are now
configured independently. Previously, both tiers shared the same timing
structure, which made it difficult to model their performance differences.

## Build Compatibility Fixes

Two compatibility issues prevented the project from compiling with newer Linux
toolchains:

- Added the missing `<limits>` include required by
  `std::numeric_limits` in `simplessd/hil/nvme/controller.cc`.
- Replaced the fixed-size `SIGSTKSZ` signal stack array with a runtime-sized
  `std::vector` in `sim/signal.cc`.

Build the latest source with:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel "$(nproc)"
```

The latest executable is:

```text
build/simplessd-standalone
```

## Independent SLC and TLC Timing

The PAL configuration now maintains separate NAND timing structures for SLC
and TLC. PAL selects the appropriate timing according to the physical block's
tier.

New SLC timing parameters:

```ini
SLCRead = 25000000
SLCWrite = 3000000
SLCErase = 1500000000
```

New TLC timing parameters:

```ini
TLCLSBRead = 40000000
TLCLSBWrite = 500000000
TLCCSBRead = 90000000
TLCCSBWrite = 900000000
TLCMSBRead = 65000000
TLCMSBWrite = 1300000000
TLCErase = 3500000000
```

All timing values use picoseconds.

The old shared timing names remain supported for compatibility:

```ini
LSBRead =
LSBWrite =
CSBRead =
CSBWrite =
MSBRead =
MSBWrite =
Erase =
```

When old timing names are used, their values are applied to both tiers.

## Configuration Files

The current dual-tier configuration is:

```text
config/dtssd.cfg
```

Important current values:

```ini
Channel = 8
Package = 4
Die = 1
Plane = 1
PageSize = 16384
DMASpeed = 400
DMAWidth = 8
```

`config/dtssd.cfg` currently uses `SLCWrite = 3000000` while
`simplessd/config/sample.cfg` uses `SLCWrite = 300000000`. Using the wrong SSD
configuration file therefore produces substantially different SLC bandwidth.

Run the dual-tier configuration explicitly:

```bash
./build/simplessd-standalone \
  ./config/sample.cfg \
  ./config/dtssd.cfg \
  ./output
```

## Trace and Tier Selection

The simple trace format is:

```text
time operation LBA NLB tier
```

Tier values:

- `0`: SLC
- `1`: TLC

Example SLC write:

```text
0 W 0 2048 0
```

Example TLC write:

```text
0 W 0 2048 1
```

With `LBASize = 512`, an `NLB` value of `2048` represents a 1 MiB request.

For maximum throughput tests, use asynchronous trace submission:

```ini
TimingMode = 1
QueueDepth = 32
```

## Per-Tier I/O Statistics

Added `generate_iostat.py`, which converts `output/request_latency.csv` into
per-simulation-second bandwidth, IOPS, and latency statistics:

```bash
python3 generate_iostat.py
```

Default output:

```text
output/iostat.csv
```

The generated CSV includes combined and per-tier fields:

```text
read_MiB_s
write_MiB_s
total_MiB_s
IOPS
avg_latency_ms
slc_read_MiB_s
slc_write_MiB_s
slc_total_MiB_s
slc_IOPS
slc_avg_latency_ms
tlc_read_MiB_s
tlc_write_MiB_s
tlc_total_MiB_s
tlc_IOPS
tlc_avg_latency_ms
```

Custom input and output paths are supported:

```bash
python3 generate_iostat.py \
  output/slc/request_latency.csv \
  -o output/slc/iostat.csv
```

## Verified Performance

Tests used 16 GiB sequential writes, 1 MiB requests, `TimingMode = 1`, and
`QueueDepth = 32`.

With SLC program latency set to 300 us:

```text
SLC peak bandwidth: approximately 1475 MiB/s
```

With SLC program latency set to 3 us:

```text
SLC sustained bandwidth: approximately 2969 MiB/s
SLC peak bandwidth: approximately 2970 MiB/s
```

With the configured TLC LSB/CSB/MSB timing:

```text
TLC sustained bandwidth: approximately 559 MiB/s
TLC peak bandwidth: approximately 560 MiB/s
```

PAL statistics confirmed that SLC and TLC requests use their corresponding
physical regions:

```text
pal.slc.program.count
pal.tlc.program.count
```

## Current Performance Bottleneck

With `SLCWrite = 3000000`, NAND cell program latency is no longer the SLC
performance bottleneck.

Approximate limits of the current configuration:

| Component | Approximate Limit |
| --- | ---: |
| PCIe Gen3 x4 | 3756 MiB/s |
| AXI 128-bit at 250 MHz | 3815 MiB/s |
| 8-channel NAND DMA at 400 MT/s | 3052 MiB/s |
| Measured SLC throughput | 2969 MiB/s |

The measured SLC throughput reaches approximately 97% of the NAND channel DMA
limit. Increasing `QueueDepth` further is unlikely to improve throughput
significantly.

To move the bottleneck closer to PCIe Gen3 x4, increase NAND DMA speed, for
example:

```ini
DMASpeed = 533
```

## Validation Commands

Confirm the actual NAND program timing used by a simulation:

```bash
grep 'pal.program.time.mem' output/log.txt
```

For `SLCWrite = 3000000`, the expected value is:

```text
pal.program.time.mem = 3000000
```

Confirm the workload's host-visible tier:

```bash
awk -F, 'NR > 1 { count[$4]++ } END { for (tier in count) print tier, count[tier] }' \
  output/request_latency.csv
```

Confirm physical PAL operations:

```bash
grep -E 'pal\.(slc|tlc)\.(read|program|erase)\.count' output/log.txt
```

## Notes

- Always use separate output directories for SLC, TLC, overwrite, and mixed
  workload tests. Reusing `output/` overwrites previous results.
- Use `build/simplessd-standalone` after rebuilding to ensure the latest source
  is executed.
- PCIe generation defines the interface ceiling; actual throughput may be
  limited by NAND program latency, channel DMA bandwidth, garbage collection,
  or available internal parallelism.
